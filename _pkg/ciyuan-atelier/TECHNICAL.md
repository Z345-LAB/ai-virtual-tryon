# 次元造物 · 技术文档

> 版本：v1.0　｜　日期：2026-10-21　｜　赛道：第九届传智杯 · AI创新应用挑战赛

---

## 1. 项目概述

「次元造物」是一个面向二次元角色的一站式换装与 3D 化工具。用户上传角色图、输入一句服装描述，系统在约 10 秒内产出保留角色特征的换装图；再点击一次，约 80 秒后得到可在浏览器中 360° 旋转的 3D 模型。

项目以「无服务器 + 双 AI 服务编排」为核心，全部功能跑在腾讯 EdgeOne Pages 上，无独立服务器、无数据库。

### 1.1 设计目标

| 目标  | 具体约束                      |
| --- | ------------------------- |
| 可用  | 任一外部服务故障时，页面不得白屏，必须给出可读原因 |
| 快   | 首屏可交互 < 1s，2D 结果 < 15s    |
| 便携  | 单机可复现，本地与线上共用同一份核心代码      |
| 安全  | API Key 绝不进入前端与版本库        |
| 可维护 | 无构建步骤，改一行即可上线             |

### 1.2 不在范围内

用户体系、作品持久化、多语言、移动端原生 App。

---

## 2. 场景与用户价值

传统「给角色换套衣服」的路径是：找画师 → 描述需求 → 等稿 → 改稿，成本数百至数千元、周期数天。

本工具把单次试错成本压到约 0.5 元 / 10 秒，把 3D 化的边际成本压到约 0.3 美元 / 80 秒。价值不在「生成一张图」，而在**让试错变得几乎免费**：用户可以连续试十套造型，再决定让画师精细绘制哪一套。

目标用户：同人创作者、独立游戏/漫剧前期概念设计、虚拟主播形象迭代。

```

│  └─ 状态栏：分阶段提示、真实进度百分比、降级原因                               │
│  public/vendor/model-viewer.min.js（本地托管，不依赖境外 CDN）                 │
└───────────────────────────────┬────────────────────────────────────────────┘
                                │ 同域 /api/*
┌───────────────────────────────▼────────────────────────────────────────────┐
│  EdgeOne Pages Cloud Functions（Node 20，单次执行上限 60s）                  │
│  cloud-functions/api/{health,tryon,create3d,check3d}.js                    │
│         │                                                                   │
│         └── _lib/                                                           │
│              ├─ wan.js     通义万相同步调用 + 参数校验 + 错误归一              │
│              ├─ three.js   Tripo v3 建任务/查任务 + 失败处理                   │
│              ├─ net.js     请求层：有 fetch 用 fetch，无则 node:https         │
│              ├─ env.js     context.env / process.env 统一读取                 │
│              └─ http.js    JSON 响应、CORS、预检                              │
└───────────┬──────────────────────────────────────┬─────────────────────────┘
            │ HTTPS                                │ HTTPS
   ┌────────▼─────────┐                  ┌─────────▼──────────┐
   │ 阿里云百炼         │                  │ Tripo v3            │
   │ wan2.7-image-pro  │                  │ image-to-model      │
   │ 同步出图 ~10s      │                  │ 异步任务 ~80s        │
   └──────────────────┘                  └────────────────────┘
```

### 3.1 为什么是「同域云函数」

- 若前端静态托管、后端另置，需要处理跨域与两套域名，且本地调试链路不同
- EdgeOne 的云函数与静态资源同域，前端只需相对路径 `/api/*`
- 本地用 Express 复刻同样的路由路径，**同一份 `_lib` 在两端运行**，本地通过即线上大概率通过

## 4. 关键流程

### 4.1 2D 换装（同步）

```
浏览器                     云函数                      通义万相
  │  POST /api/tryon          │                            │
  │  {image_base64, prompt}   │                            │
  ├──────────────────────────►│  校验 MIME / 归一 data URI   │
  │                           │  拼接系统提示词（锁定角色特征） │
  │                           ├──── POST generation ───────►│
  │                           │                            │ 模型推理
  │                           │◄──── 200 {choices[0]} ─────┤  ~10s
  │                           │  取 content[].image         │
  │◄── {image_url} ───────────┤                            │
```

**为什么同步**：万相的异步模式需要「建任务 → 每 3 秒轮询」，最长 150 秒，超出云函数 60 秒上限。同步模式一次请求拿图，实测 10 秒，比异步（16 秒）更快且少 N 次请求。

### 4.2 3D 生成（异步 + 前端轮询）

```
浏览器                云函数                      Tripo v3
  │ POST /api/create3d   │                            │
  ├─────────────────────►│  POST /generation/image-to-model
  │                      ├───────────────────────────►│
  │                      │◄──── {task_id} ────────────┤
  │◄── {task_id, demo} ──┤                            │
  │                      │                            │  生成中
  │ 每 3s GET /check3d   │                            │
  ├─────────────────────►│  GET /tasks/{id}           │
  │                      ├───────────────────────────►│
  │◄─ {status, progress} ┤                            │
  │      …直到 success    │                            │
  │  取 output.model_url → model-viewer 加载           │
```

**注意**：Tripo 的输出链接仅 5 分钟有效，因此模型必须在生成成功后立刻加载或下载。

## 5. 技术选型与取舍

### 5.1 前端：原生单文件 vs 框架

| 方案             | 结论                                           |
| -------------- | -------------------------------------------- |
| React/Vue + 构建 | 引入 node_modules、构建产物、CI 步骤；本项目 UI 复杂度不足以抵消成本 |
| **原生单文件**      | ✅ 无构建、EdgeOne 直接托管、改一行即上线、评委可读源码             |

代价：样式与逻辑内联，文件较长（约 1300 行）。通过区块注释分区缓解。

### 5.2 3D 渲染：model-viewer vs Three.js

`model-viewer` 是 Google 的 Web Component，一行标签即可获得：轨道控制、自动旋转、环境光照、进度事件、GLB 解码。

自研 Three.js 需处理加载器、相机、光照、控制、色调映射，代码量与故障面都显著更大。**本项目 3D 只是展示环节，不值得自研。**

### 5.3 图像模型：wan2.7-image-pro

- 支持「图 + 文」多模态输入，天然适配"保留角色特征、只换服装"
- 同步接口一次出图，便于在云函数里跑
- 输出 1K PNG 约 1.6MB、2K 约 5.4MB，可通过 `WAN_SIZE` 调节

### 5.4 3D 模型：Tripo v3 vs v2

|      | v2                                            | **v3**        |
| ---- | --------------------------------------------- | ------------- |
| 图片传入 | 必须先 `POST /upload` 拿 `image_token`（multipart） | **直接传公网 URL** |
| 依赖   | 需要 fetch + FormData                           | 只需 JSON POST  |
| 结论   | 在裁剪过的运行时里跑不通                                  | ✅ 采用          |

v3 的 `face_limit` 参数可以把 139 万面压到 3 万面（体积从 42 MB 降到 4.98 MB），且不加价。

**这个参数经历过一次决策反复，过程比结论更有价值**：

1. 最初因为 42 MB 模型在浏览器里转不动，先设 `face_limit=30000` 保可用性；
2. 后来发现"转不动"的真正原因是**本机代理导致大文件下载极慢**，与面数无关——用 5 MB 的模型
   在同样条件下也触发了同样的超时；
3. 关掉代理后实测全精度模型可正常加载，于是改回全精度，同时把加载超时从 60 秒放宽到 90 秒，
   并给下载缓存加 12 MB 体积守卫（超过则不驻留内存，改为点击时再取）。

最终配置：全精度（约 145 万面 / 40 MB），弱网仍可能较慢，此时会明确提示而不是静默降级。

## 6. 核心实现

### 6.1 请求层双通道（net.js）

部分 Serverless 运行时提供 `Request`/`Response` 但没有全局 `fetch`（本项目线上曾实测报 `fetch is not defined`）。因此请求层做成双通道：

```js
const send = typeof fetch === 'function' ? viaFetch : viaHttps;
```

- 有 `fetch`：走标准 `fetch` + `AbortSignal.timeout`
- 无 `fetch`：走 `node:https`，手写超时与 JSON 解析，超时统一抛 `TimeoutError`，上层逻辑无需分支

**设计要点**：让修复在"两种假设"下都成立，不赌根因。

### 6.2 3D 任务无状态化

云函数是分布式、无共享内存的。若把任务状态存在进程内 `Map`，换个节点就读不到。

方案：`task_id = t3d_<base36(时间戳)>`，查询时解析时间戳，`elapsed >= 2000ms` 即视为完成。任何节点算出同一结果。

副作用：无法保存真实模型中间态。因此该方案**仅用于演示降级路径**，真实 3D 走 Tripo 的 task_id。

### 6.3 失败处理：可见地失败，而不是假装成功

2D 与 3D 两段的外部依赖不同，失败策略也不同：

| 层级 | 触发条件 | 用户可见结果 |
| --- | --- | --- |
| L1 | 未配置密钥 | 明确提示"服务端未配置 ALIYUN_API_KEY / TRIPO_API_KEY"，不发起请求 |
| L2 | 接口返回非 0 码（如 2010 余额不足） | 提示具体错误码与余额，3D 段直接失败 |
| L3 | 请求超时 / 网络不可达 | 提示底层错误（如 ENOTFOUND），允许重试 |
| L4 | 模型已生成但浏览器加载失败 | 保留换装图，90 秒后提示加载失败并提供重试 |

**3D 段的特殊约定**：服务端在 Tripo 不可用时会返回一个降级任务占位，但**前端把它当作失败处理**
（`if (checkData.demo) throw`），不会把演示模型当成用户作品展示。用户看到的是
"当前不可用 + 原因 + 可重试"，而不是一个"看起来成功了"的假结果。

**统一原则**：失败必须可见、可重试。宁可显示"当前不可用 + 原因"，也不能让界面无限转圈，
更不能用一个演示模型冒充真实结果。

### 6.4 前端状态与体验

- **分阶段提示**：把 10 秒的等待拆成"解析参考图 → 理解描述 → 生成中"等多段，降低感知等待
- **真实进度**：3D 阶段读取 `check3d` 返回的 `progress`；模型下载阶段监听 `model-viewer` 的 `progress` 事件
- **超时兜底**：90 秒未 `load` 判定为失败，保留换装图并说明原因（全精度模型约 40 MB，阈值过短会误杀）
- **组件守卫**：`ensureModelViewerReady` 在 8 秒内轮询 `customElements.get('model-viewer')`，避免自定义元素未注册导致 `src` 设置完全无效

### 6.5 本地持久化（IndexedDB）

生成结果默认是临时链接（图片 24 小时、模型 5 分钟），刷新即失效。为了让"试过的造型"可回溯，
前端用 IndexedDB 做本地作品集：

| 项 | 实现 |
| --- | --- |
| 数据库 / 表 | `ciyuan-atelier` / `generations`（`keyPath: 'id'`，索引 `createdAt`） |
| 容量策略 | 最多 20 条，写入后按 `createdAt` 倒序裁剪，超出即删除最旧记录 |
| 保存内容 | 底图、描述词、三个候选方案、已缓存模型（Blob）、创建时间 |
| 可做的事 | 查看、恢复、再次编辑、删除 |
| 刷新之后 | 底图、描述、候选、模型均可恢复（模型已转存为 Blob，不再依赖 5 分钟链接） |

**为什么选 IndexedDB 而不是 localStorage**：模型是二进制大对象，localStorage 只能存字符串且上限约 5 MB；
IndexedDB 可直接存 Blob，容量按配额走。写入前对候选图与模型做体积判断，避免把配额吃满。

**刻意不做的事**：不做云端同步、不做账号体系。历史只属于当前浏览器，换设备或清缓存即丢失——
这一点在界面上明说，避免用户误以为存在云端。

### 6.6 二次微调：只载入，不生成

选定作品后提供四个微调入口：仅改配色、仅改材质、减少配饰、自定义微调。

关键在于**它们不发起请求**：

1. 把当前选定的图载入为新底图
2. 把对应的约束描述写进输入框（如"保持面部、发型、体型、版型一致，只调整服装配色"）
3. 状态栏提示"已载入，确认后主动点击开始换装，本操作尚未生成新图"

**为什么这样设计**：微调是最容易被误触的操作，而每次换装都要花钱。把"改描述"和"花钱生成"拆成两步，
用户可以先看清描述再决定。这是把成本控制做进交互，而不是只写在文档里。

### 6.7 真实结果与主动下载

- **没有真实模型时禁止下载**：`downloadModel` 前置校验 `state.modelIsReal`，演示模型不会被导出
- **角色卡需主动点击**：用 Canvas 合成卡片（作品 + 描述 + 水印），用户点击才绘制并下载
- **任何文件都不自动下载**：图片、角色卡、模型全部由用户主动触发

**原因**：自动下载在演示场景里是干扰（浏览器弹出下载栏、文件堆在下载目录），
更重要的是——它会让人分不清"这是真结果还是兜底产物"。主动下载把判断权交回用户。

### 6.8 输入校验与接口收敛

| 位置 | 校验 |
| --- | --- |
| 前端上传 | 仅 JPG / PNG / WEBP；单张 ≤ 12 MB；类型与体积在读取前拦截 |
| 后端换装接口 | 校验 data URL 的 MIME；描述词必须为非空字符串且 ≤ 1000 字符 |
| 描述输入框 | `maxlength="1000"`，与后端上限一致 |

**健康检查接口做了收敛**：上线初期 `/api/health` 会返回模型名、服务商地址、密钥长度、Node 版本、
运行时能力等排障信息；这些信息对前端无用，却等于把内部结构公开给任何访问者。
现在只返回四项：`ok`、`api_key_configured`、`tripo_key_configured`、`time`。

## 7. 部署与运维

### 7.1 部署拓扑

单项目、单域名：静态资源走 CDN，`/api/*` 走云函数。加速区域选「全球（不含中国大陆）」，免 ICP 备案。

### 7.2 配置项

| 变量                 | 作用       | 缺省                  |
| ------------------ | -------- | ------------------- |
| `ALIYUN_API_KEY`   | 百炼鉴权     | 无（2D 不可用）           |
| `TRIPO_API_KEY`    | Tripo 鉴权 | 无（3D 降级）            |
| `TRIPO_FACE_LIMIT` | 输出面数上限   | 不限制                 |
| `WAN_SIZE`         | 输出尺寸     | `2K`                |
| `DEMO_MODEL_URL`   | 降级模型     | `/models/robot.glb` |

### 7.3 自检接口

`GET /api/health` 只返回四项：`ok`、`api_key_configured`、`tripo_key_configured`、`time`。
部署后先看这个接口，确认两个密钥都已生效，再点页面——这是排障最快的一步。

早期版本会返回模型名、服务商地址、密钥长度与运行时能力，排障方便但等于公开内部结构，
现已全部收敛。排障细节改为只在服务端日志输出。

### 7.4 已知运维注意事项

- 云函数配置变更后需重新部署才生效
- 控制台"已部署"与边缘"已生效"存在时间差，验证需带缓存破坏参数（`?v=xxx`）
- 输出目录必须是 `public`，否则根目录无 `index.html` 会 404

## 8. 性能与成本

### 8.1 实测数据

| 环节 | 耗时 / 体积 |
| --- | --- |
| 2D 单张换装（同步调用） | 10 s，输出 1.6MB（1K）/ 5.4MB（2K） |
| 2D 三候选（并行三次） | 约 30 s 出齐（单张并行，不是三倍串行） |
| 四视图扩图 `image-to-multiview` | 21 s |
| 3D 重建 `multiview-to-model`（当前默认） | 98 s，40.7MB，145 万面 |
| 3D 单图重建 `image-to-model`（早期实测） | 86 s，42.1MB，139 万面 |
| 3D 单图 + `face_limit=30000`（弱网方案） | 80 s，**4.98MB**，29,782 面 |
| 演示模型加载（本地 464KB） | 0.011 s |

> 面数随输入不同在 139–145 万之间浮动，体积约 40–42 MB。完整链路（三候选 + 四视图重建）
> 端到端约 130 秒。

### 8.2 成本

| 项 | 单价 |
| --- | --- |
| 万相出图 | 约 0.5 元/张（一次三候选 ≈ 1.5 元） |
| Tripo 四视图扩图 `image-to-multiview` | 约 10 credits |
| Tripo 3D 重建（四视图 / 单图） | 20–30 credits |
| 完整 3D（四视图，当前默认） | 约 30–40 credits ≈ 0.3–0.4 美元/次 |
| 托管 | EdgeOne 免费额度（100 万次函数调用/月） |

> 成本上最关键的一条：**三张候选只做 2D 比较，3D 只跑选中的那一张**——
> 若三张都建模，单次交互成本会变成三倍。

### 8.3 一个反直觉的结论

模型体积主要不是贴图造成的。42MB 的模型里贴图仅 4.17MB，其余约 38MB 全是网格数据（72 万顶点 / 139 万三角面）。因此**限面数比降贴图质量有效得多**——这条结论在技术上成立，但最终产品没有采用限面数方案，
因为后来查明"加载慢"的真实原因是本机代理导致大文件下载受阻，与面数无关。最终选择保留全精度，
用放宽超时（90 秒）与下载缓存体积守卫来兜底（详见 5.4 与 6.3）。

## 9. 问题复盘

| 现象                     | 初始猜测      | 实测结论                                      | 修复                                |
| ---------------------- | --------- | ----------------------------------------- | --------------------------------- |
| 首页 404                 | 代码没推上去    | 远端已是最新，`index.html` 已移入 `public/`，输出目录仍是根 | 改输出目录                             |
| `fetch is not defined` | Node 版本过低 | 运行时为 v20.19.3 且有 fetch，但请求路径仍失败           | 加 `node:https` 双通道                |
| 3D 一直在"载入中"            | 模型太大      | 5MB 同样不触发 `load`                          | 组件本地化 + 取消 `display:none` + 8 秒守卫 |
| 42MB 模型转不动             | 模型面数过高    | 真正原因是本机代理导致大文件下载极慢，5MB 模型同样超时             | 关代理后改回全精度；超时 60→90s，缓存加 12MB 守卫 |
| 部署后配置不生效               | 变量拼错      | 构建未完成 / 缓存                                | 带 `?v=` 重查 health                 |

**方法论**：每个"看起来合理"的解释，都要用一个可测量的量去证伪。

## 10. 局限与演进

### 10.1 当前局限

- 3D 生成受第三方速度制约，现场演示需预留 90 秒
- 模型与图片均为临时链接（5 分钟 / 24 小时），未做持久化
- 历史仅存于浏览器本地（IndexedDB，最多 20 条），换设备或清缓存即失去
- 全精度模型约 40 MB、145 万面，弱网加载慢，且不适合移动端长时间展示

### 10.2 演进方向

1. **产物持久化**：当前作品集只存在浏览器本地，下一步转存对象存储，实现跨设备作品集
2. **异步化体验**：3D 生成期间允许用户继续操作，完成后通知
3. **提示词工程**：把"换装描述"做成风格模板库，降低输入门槛
4. **多视图重建**：用正面 + 侧面两张图生成更准确的角色模型
5. **导出格式**：支持 FBX/OBJ/USDZ，直接进 Unity/Blender
