问题：没有 `package.json`、没有 `.gitignore`、密钥直接写在代码里、`functions/tryon.js` 引用了 `public/` 但那个目录不存在。

## 人的意图（原话）

> 我这边主要是把产品和方向定清楚，工程细节请你多带一步。我在准备 vibe coding 的比赛，要求提交细颗粒度的历史记录到 GitHub，所以每一步都告诉我为什么这么做；能直接做的你就做完，我只需要知道往 Git 上传时该写什么备注。要用的 key 都在密钥文档里。

这句话定义了整个协作模式：**「能干的直接干」+「提交备注由 AI 给、推送由人来点」**。

## AI 的判断与动作

| # | 动作                                                       | 依据                          |
| - | -------------------------------------------------------- | --------------------------- |
| 1 | 先读 git 状态，而不是直接改代码                                       | 已有 4 个提交、远程已配置，避免误伤历史       |
| 2 | 全盘搜索密钥文档，定位到 `D:\zrb\密钥.docx`                            | 用户说"在密钥 word 文档里"，但不能假设路径   |
| 3 | 从 docx 的 `word/document.xml` 抽文本，按「标签行 → 下一行才是 key」的结构解析 | 直接 unzip + 去标签比装 Office 库更轻 |
| 4 | 密钥写入 `.env`，并立刻确认它被 `.gitignore` 忽略                      | 这是"密钥绝不入库"的唯一保险             |
| 5 | 用不存在的任务 ID 调接口，返回 200 即说明鉴权通过                            | 比直接生成一张图更省额度，先验证再花钱         |
| 6 | 真实跑一次换装，确认端到端                                            | 16 秒出图，证明链路通                |

**关键取舍**：面对"密钥在文档里"这种模糊信息，AI 没有让用户手动粘贴，而是自己找到文档、自己抽取、自己写入 `.env`，并输出**脱敏后的密钥指纹**（`sk-ws-…Lu_A`）供人核对——既不泄露，又能确认取对了。

## 提交拆分策略

没有把所有改动塞进一个 commit，而是按**关注点**拆成 5 个：

```
chore: 初始化 Node 工程，补齐 express/cors/dotenv 依赖
chore: 增加环境变量模板与 .gitignore
fix(server): 修复服务无法启动、首页 404 与跨域被拦
fix(web): 修复接口地址解析、描述框默认值与 3D 加载卡顿
docs: 补充 README，说明运行方式、接口与实现状态
```

理由：赛道要求「细颗粒度、禁止一次性提交」，而"一次提交对应一个功能模块的落地"最自然的切法就是按文件关注点。

## 一次重要的规则确立

> 用户：推送这一步我自己来，你只负责生成文件，推不推、什么时候推由我决定。

这条约束被写进了 AI 的长期记忆，并在后续所有阶段严格执行：AI 只做 `git add` / `git commit` / 展示待推列表，**最后一步 `git push` 永远由人点**。

这也是本项目"人引导意图"的一个具体体现——**提交节奏和发布时机属于人的决策，不属于 AI**。
