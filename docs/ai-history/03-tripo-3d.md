## 人的意图（原话）

> 现在就接上吧。

一句话授权，但 AI 面对的真实环境很糟：密钥在文档里、域名可能被墙、账户可能没额度。所以策略是**先探路，再写代码**。

## 第一次探路：域名与密钥

```
nslookup api.tripo3d.ai  →  31.13.94.23   ← Facebook 的 IP，典型的 DNS 污染
DoH 查真实 IP            →  74.86.12.173
直连真实 IP              →  超时（IP 级封锁）
```

于是换思路，逐个探测候选域名：

```
api.tripo3d.com      → 200/404（通）
openapi.tripo3d.com  → 401（通，是 API 网关）
```

同一把 key 在 `api.tripo3d.com` 上**鉴权通过**——说明国内站可用，国际站不可用。

> AI 的判断：不去绕过封锁，而是**找到同一服务的国内入口**。这是工程上更稳的解法。

## 第二次探路：额度

```
GET  /v2/openapi/user/balance  →  {"balance":0}
POST /v2/openapi/task          →  403 code 2010 "You don't have enough credit"
```

链路是通的（上传、建任务都发出去了），只差额度。

## 一次被推翻的推断

> 用户：tripo 不是有免费额度吗？

AI 起初把原因归为"额度在国际站钱包"，还写了一版「按余额自动挑站点」的代码。但用户随后明确：

> 这个余额行为就不要说明上传 git 了，直接跳过到下一步骤。

AI **立即 `git checkout` 撤回未提交的改动**，工作区回到上一个提交。理由：这是产品取舍问题，不是技术问题，人已经拍板，AI 不纠缠。

后来查证：Tripo 的 **Studio 网页积分与 API credits 是两套独立账目**，网页显示 300 不代表 API 可用。这个结论最终写进 README，避免误导后来者。

## 核心设计：四级降级

外部服务不稳定，不能让它变成"页面白屏"。所以设计成**任何一步失败都有可见的降级**：

| 失败点 | 用户看到 |
|---|---|
| 没配 Key | 演示模型 + "未配置 TRIPO_API_KEY" |
| 余额不足 | 演示模型 + "额度不足（当前余额 0）" |
| 网络不通/超时 | 演示模型 + 具体错误码 |
| 模型拉取失败 | 退回显示静态预览图 |

关键点：**降级不是静默的**，状态栏一定说明原因。宁可承认「3D 不可用」，也不能让使用者以为页面卡死。
